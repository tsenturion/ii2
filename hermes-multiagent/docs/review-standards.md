# Стандарт проверки кода

Этот документ содержит обязательные правила автоматической и ручной проверки кода учебного проекта.

## SEC-01 — Параметризованные SQL-запросы

SQL-запросы нельзя строить прямой подстановкой пользовательских данных через f-строки, конкатенацию строк или `format`.

Для PostgreSQL значения необходимо передавать отдельно через параметры драйвера. Нарушение считается проблемой безопасности.

## ERR-01 — Ошибки не должны исчезать бесследно

Нельзя перехватывать `Exception` и скрывать ошибку без диагностического логирования, повторного возбуждения исключения или другой явно определённой обработки.

Конструкция `except Exception: return False` считается нарушением, если причина ошибки полностью теряется.

## COR-01 — Наблюдаемое поведение должно сохраняться

Изменение не должно случайно нарушать существующий публичный контракт функции, сервиса или API.

Если при проверке обнаружено изменение поведения, необходимо указать конкретный сценарий, в котором оно проявляется.

## ARC-01 — Ответственности должны быть разделены

Слой работы с данными отвечает за взаимодействие с хранилищем.

Логика HTTP, пользовательского интерфейса и инфраструктуры не должна без необходимости смешиваться с кодом репозитория данных.

## REV-01 — Только проверяемые и полезные замечания

Каждый комментарий должен содержать конкретную проблему, объяснение последствий и, когда возможно, способ исправления.

Мелкие стилистические вопросы, которые автоматически решаются форматтером или линтером, не следует публиковать как отдельные замечания.

## SUG-01 — Suggestions должны быть безопасными и локальными

GitHub Suggestion разрешено создавать только тогда, когда исправление однозначно и не требует дополнительных бизнес-решений.

Если существует несколько архитектурно допустимых решений, необходимо описать проблему без автоматического предложения замены.
