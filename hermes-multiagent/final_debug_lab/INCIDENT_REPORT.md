# Отчёт об инциденте BUG-001: сбой возврата для старого заказа

## Краткое резюме

При оформлении возврата для одного из перенесённых заказов операция завершалась ошибкой, хотя новый заказ с теми же параметрами обрабатывался успешно. Причина — дата получения в legacy-данных была представлена ISO-строкой, тогда как сервис возвратов выполняет вычисления с объектом `date`. На границе legacy-адаптера значение нормализовано в `date`; после исправления оба сценария из воспроизведения создают заявку со статусом `requested`.

## Влияние

Для заказов, в которых `delivered_at` оставался строкой, создание заявки на возврат прерывалось до расчёта суммы и сохранения заявки. В подтверждённом сценарии затронут заказ 1002; заказ 1001 с датой типа `date` работал. Данных о масштабе за пределами этого учебного воспроизведения нет.

## Хронология диагностики

1. В `BUG_REPORT.md` зафиксировано, что заказ 1001 проходит, а старый заказ 1002 при тех же параметрах завершается ошибкой; точная причина на тот момент была неизвестна.
2. В сохранённом журнале до исправления заказ 1001 успешно обработан. Для заказа 1002 журнал показывает `delivered_at='2026-09-10'`, после чего записан traceback.
3. Traceback указывает на вычитание `delivered_at` из `today` в `RefundService.create_request`. Сопоставление с `legacy_orders.py` выявляет несовпадающие представления: у одного заказа дата уже имеет тип `date`, у другого хранится ISO-строкой.
4. В legacy-адаптере добавлено преобразование строкового `delivered_at` через `date.fromisoformat`. Исправление локализовано на границе интеграции, чтобы сервис возвратов получал нормализованную дату и не зависел от формата старого источника.
5. В сохранённом журнале после исправления оба заказа обработаны успешно; для каждого записан возврат на `90.00` со статусом `requested`.

## Наблюдаемый симптом

При одинаковом запросе на возврат заказ 1001 проходил, а заказ 1002 завершался исключением. Различие в журнале — тип значения `delivered_at`: `datetime.date` у успешного заказа и строка у проблемного.

## Непосредственный технический сбой

Вычисление `(today - delivered_at).days` получило `datetime.date` и `str`. Python выбросил `TypeError: unsupported operand type(s) for -: 'datetime.date' and 'str'`. До расчёта суммы и вызова репозитория для создания заявки выполнение не дошло.

## Корневая причина

Данные legacy-источника не имели единого типа для даты получения: в частности, для заказа 1002 она хранилась как строка ISO-формата. Перед исправлением это значение доходило до сервиса без нормализации. Сервис корректно рассчитывал, что получает дату, и не преобразовывал строковые значения.

## Подтверждающие эксперименты

- В журнале до исправления успешно обработанный заказ 1001 содержит `datetime.date(2026, 9, 10)`; заказ 1002 содержит строку `'2026-09-10'` и падает на вычитании даты.
- После исправления журнал показывает `datetime.date(2026, 9, 10)` для обоих заказов и успешное создание возврата со статусом `requested`.
- Регрессионный тест получает заказ 1002 через `get_order` и проверяет идентификатор заказа, сумму `90.00` и статус `requested`. До исправления тест воспроизвёл `TypeError`, после исправления прошёл.

## Минимальное исправление и граница адаптера

Адаптер `get_order` преобразует `delivered_at` только тогда, когда исходное значение — строка, используя `date.fromisoformat`; уже типизированное значение остаётся без изменений. Это минимально устраняет несовместимость legacy-формата, сохраняя единый тип на выходе адаптера. Исправление находится именно на границе legacy-адаптера, чтобы не переносить обработку устаревших форматов в бизнес-логику возвратов и не менять её расчёты и правила.

## Регрессионный тест

`test_legacy_order_creates_refund_request` воспроизводит путь для заказа 1002 через адаптер и сервис возвратов, затем проверяет, что заявка создана для заказа 1002, сумма равна `90.00`, а статус — `requested`. Тест защищает от повторного пропуска строковой даты до сервиса.

## Результаты проверки до и после

- До исправления: заказ 1001 — заявка создана на `90.00`, статус `requested`; заказ 1002 — `TypeError` при вычитании строки из даты, заявка не создана.
- После исправления: оба заказа — заявки созданы на `90.00`, статус `requested`.
- После исправления целевой регрессионный тест прошёл, затем успешно завершился связанный набор из 18 тестов `testing_lab` и `final_debug_lab`.

## Меры предотвращения

- Сохранять регрессионный сценарий со старым заказом и проверять не только отсутствие исключения, но и сумму, идентификатор заказа и статус заявки.
- На границах интеграции нормализовать legacy-представления и проверять типы значений перед передачей в доменную логику.
- При изменении формата данных добавлять проверки совместимости для старых и новых записей; ошибки обработки фиксировать с контекстом заказа и traceback, не подавляя их.
