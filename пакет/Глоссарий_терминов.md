# Глоссарий терминов курса «Мультиагентные ИИ-системы»

## Искусственный интеллект и языковые модели

| Термин | Понятное объяснение |
|---|---|
| Искусственный интеллект, ИИ (Artificial Intelligence, AI) | Общее название технологий, которые выполняют задачи, обычно требующие человеческого анализа: распознают данные, создают текст, планируют действия или принимают решения. |
| Машинное обучение (Machine Learning, ML) | Подход, при котором программа выявляет закономерности на примерах данных, а не получает все правила в виде вручную написанного кода. |
| Генеративный ИИ (Generative AI) | ИИ, который создаёт новое содержимое: текст, код, изображения, звук или другие данные. |
| Нейронная сеть | Математическая модель из связанных вычислительных слоёв. Во время обучения она настраивает внутренние параметры, чтобы находить закономерности в данных. |
| Большая языковая модель (Large Language Model, LLM) | Нейронная модель, обученная работать с естественным языком и кодом. Она предсказывает продолжение последовательности токенов и благодаря этому может отвечать на вопросы, писать тексты и решать задачи. |
| Модель | Конкретная обученная система ИИ, которая принимает входные данные и формирует результат. Разные модели отличаются качеством, скоростью, стоимостью и доступными возможностями. |
| Параметр модели | Числовое значение внутри нейронной сети, настроенное во время обучения. Совокупность параметров определяет поведение модели. |
| Токен | Небольшая единица текста, с которой работает языковая модель. Токеном может быть слово, часть слова, знак препинания или фрагмент кода. |
| Контекстное окно (Context Window) | Максимальный объём токенов, который модель может одновременно учитывать: инструкции, историю диалога, документы, код и собственный ответ. |
| Инференс (Inference) | Процесс использования уже обученной модели для получения ответа на новый запрос. |
| Обучение модели (Training) | Процесс настройки параметров модели на большом наборе примеров. Обычно он требует значительных вычислительных ресурсов. |
| Дообучение (Fine-tuning) | Дополнительное обучение готовой модели на специализированных примерах, чтобы изменить или уточнить её поведение. |
| Промпт (Prompt) | Инструкция или набор входных данных, переданных модели. Хороший промпт описывает контекст, задачу, ограничения и ожидаемый результат. |
| Системная инструкция (System Prompt) | Инструкция самого высокого уровня, задающая роль модели, общие правила и границы поведения в текущем приложении. |
| Пользовательский запрос (User Prompt) | Конкретная задача или сообщение, которое пользователь отправляет модели. |
| Ответ модели (Model Output) | Текст, код, структурированные данные или команда инструмента, сформированные моделью. Ответ нужно проверять, потому что он не гарантированно верен. |
| Инженерия промптов (Prompt Engineering) | Практика формулирования и улучшения инструкций, чтобы ответы модели были более точными, полезными и воспроизводимыми. |
| Структурированный вывод (Structured Output) | Ответ в заранее заданной форме, например JSON по определённой схеме. Такой результат проще автоматически проверять и передавать другим компонентам. |
| Температура (Temperature) | Настройка степени случайности генерации. Низкие значения обычно делают ответы стабильнее, высокие - разнообразнее. |
| Детерминированность | Свойство процесса при одинаковом входе давать одинаковый результат. Ответы языковых моделей часто не полностью детерминированы. |
| Галлюцинация модели | Убедительно сформулированная, но неверная или выдуманная информация в ответе модели. |
| Привязка к источникам (Grounding) | Связывание ответа модели с проверяемыми данными: документами, результатами поиска, базой знаний или выводом инструмента. |
| Мультимодальность | Способность модели работать с несколькими типами данных, например одновременно с текстом и изображениями. |
| Снимок модели (Model Snapshot) | Зафиксированная версия модели. Использование конкретного снимка помогает избежать неожиданных изменений поведения после обновлений. |
| Задержка (Latency) | Время от отправки запроса до получения ответа. Для автодополнения кода обычно особенно важна низкая задержка. |
| Пропускная способность (Throughput) | Количество запросов или объём данных, которые система может обработать за единицу времени. |
| Стоимость запроса | Расход ресурсов или денег на обработку запроса моделью. Часто зависит от модели и числа входных и выходных токенов. |
| Оценивание модели (Evaluation, Eval) | Систематическая проверка качества модели или агентной системы на заранее подготовленных задачах и критериях. |
| Бенчмарк (Benchmark) | Набор стандартных задач и метрик, используемый для сравнения моделей или систем. |

## Ассистенты, агенты и мультиагентные системы

| Термин | Понятное объяснение |
|---|---|
| ИИ-ассистент | Система, которая помогает пользователю выполнить отдельное действие: объясняет, предлагает вариант, дополняет код или редактирует текст. Обычно пользователь управляет каждым следующим шагом. |
| ИИ-агент | Система на основе модели, которая получает цель, планирует несколько шагов, использует инструменты, наблюдает результаты и корректирует дальнейшие действия. |
| Автономность | Степень самостоятельности агента. Чем она выше, тем больше решений агент принимает без подтверждения человека и тем важнее ограничения и контроль. |
| Агентный цикл (Agent Loop) | Повторяющаяся последовательность: понять состояние, выбрать действие, выполнить его, получить наблюдение и решить, что делать дальше. |
| Действие агента (Action) | Конкретный шаг агента: чтение файла, вызов API, запуск теста, поиск данных или изменение кода. |
| Наблюдение (Observation) | Результат выполненного действия, который возвращается агенту: содержимое файла, вывод команды, ошибка или ответ сервиса. |
| Рефлексия (Reflection) | Дополнительный этап, на котором агент оценивает собственный результат, ищет недостатки и решает, нужна ли корректировка. |
| Инструмент агента (Tool) | Разрешённая функция, через которую агент взаимодействует с внешней средой: читает данные, запускает программу или обращается к сервису. |
| Вызов функции (Function Calling) | Способ, при котором модель не пишет свободный текст, а выбирает зарегистрированную функцию и формирует для неё структурированные аргументы. |
| Интерфейс агент-компьютер (Agent-Computer Interface, ACI) | Набор инструментов, форматов и правил, через которые агент взаимодействует с компьютером. Понятный ACI уменьшает число ошибок агента. |
| Одноагентная система (Single-agent System) | Система, в которой одна агентная роль выполняет задачу целиком. Это обычно проще в реализации и отладке. |
| Мультиагентная система (Multi-agent System) | Система из нескольких агентов или ролей, которые разделяют работу, обмениваются результатами и совместно достигают общей цели. |
| Роль агента | Закреплённая ответственность агента, например планировщик, разработчик, тестировщик или ревьюер. |
| Планировщик (Planner) | Роль, которая разбивает цель на шаги, определяет порядок работы и зависимости между задачами. |
| Исполнитель (Executor) | Роль, которая выполняет конкретные действия по подготовленному плану. |
| Ревьюер (Reviewer) | Роль, которая проверяет результат, ищет дефекты и сопоставляет работу с требованиями и стандартами. |
| Оркестратор (Orchestrator) | Компонент, управляющий порядком запуска агентов, передачей данных, состояниями, повторами и завершением общего процесса. |
| Оркестрация | Координация нескольких действий, сервисов или агентов в единый управляемый процесс. |
| Делегирование | Передача подзадачи другому агенту или специализированной роли с понятными входами, границами и ожидаемым результатом. |
| Передача управления (Handoff) | Формальный переход задачи от одного агента к другому вместе с необходимым контекстом и текущим состоянием. |
| Рабочий процесс (Workflow) | Заранее определённая последовательность шагов и переходов. В отличие от полностью автономного агента, workflow обычно имеет более предсказуемый маршрут. |
| Цепочка промптов (Prompt Chaining) | Workflow, в котором результат одного запроса становится входом следующего. Сложная задача последовательно разбивается на простые этапы. |
| Маршрутизация (Routing) | Выбор подходящего обработчика, модели или агента в зависимости от типа входной задачи. |
| Параллельное выполнение | Одновременный запуск независимых подзадач. Оно ускоряет работу, но требует аккуратного объединения результатов. |
| Контракт подзадачи | Явное описание входных данных, ожидаемого результата, ограничений и критериев готовности делегированной работы. |
| Человек в контуре (Human-in-the-loop) | Схема, в которой человек подтверждает важные решения, проверяет результат или вмешивается при риске и неопределённости. |
| Контрольная точка (Checkpoint) | Момент, в котором состояние работы сохраняется или передаётся человеку для проверки перед продолжением. |
| Ограничитель (Guardrail) | Правило или программная проверка, не позволяющая агенту выполнять опасные, запрещённые или некорректные действия. |
| Условие остановки (Stopping Condition) | Явное правило завершения цикла: цель достигнута, превышен лимит шагов, возникла ошибка или требуется решение человека. |
| Тайм-аут (Timeout) | Максимально допустимое время выполнения операции. После его истечения операция прекращается или считается неуспешной. |
| Повторная попытка (Retry) | Новый запуск временно неуспешной операции. Число повторов должно быть ограничено. |
| Задержка между повторами (Backoff) | Постепенное увеличение паузы перед следующей попыткой, чтобы не перегружать нестабильный сервис. |
| Резервный сценарий (Fallback) | Безопасный альтернативный путь, используемый, когда основной способ не сработал. |
| Состояние (State) | Данные о текущем положении процесса: выполненные шаги, промежуточные результаты, ошибки и ожидающие задачи. |
| Память агента (Memory) | Механизм сохранения информации между шагами или сессиями. Память не равна контекстному окну и обычно хранится во внешнем хранилище. |
| Сессия | Отдельная последовательность взаимодействий с сохранённой историей и состоянием. |
| Контекст проекта | Информация о структуре, правилах, коде и целях конкретного проекта, необходимая агенту для правильной работы. |
| Закреплённая сессия | Сессия, постоянно связанная с конкретным проектом или задачей, чтобы не восстанавливать рабочий контекст с нуля. |

## Контекст, поиск и RAG

| Термин | Понятное объяснение |
|---|---|
| Инженерия контекста (Context Engineering) | Проектирование всего набора информации, доступного модели: инструкций, истории, инструментов, найденных документов и текущего состояния задачи. |
| База знаний (Knowledge Base) | Организованное хранилище документов и фактов, из которого система получает сведения для ответа. |
| RAG (Retrieval-Augmented Generation) | Подход, при котором система сначала находит относящиеся к запросу материалы, а затем передаёт их модели для подготовки ответа. |
| Поиск информации (Retrieval) | Получение наиболее подходящих документов или фрагментов по запросу пользователя. |
| Индексирование | Подготовка документов к быстрому поиску: чтение, разбиение, вычисление признаков и сохранение в индексе. |
| Индекс | Структура данных, ускоряющая поиск. В RAG индекс связывает фрагменты текста с их векторными представлениями и метаданными. |
| Переиндексация | Повторное построение индекса после изменения документов, модели эмбеддингов или правил разбиения. |
| Фрагмент (Chunk) | Небольшая часть исходного документа, которая индексируется и возвращается поиском как самостоятельная единица. |
| Размер фрагмента (Chunk Size) | Объём текста в одном фрагменте. Слишком маленький фрагмент теряет контекст, слишком большой содержит лишние сведения. |
| Перекрытие фрагментов (Chunk Overlap) | Повторение нескольких строк или токенов в соседних фрагментах, чтобы смысл на границе не потерялся. |
| Эмбеддинг (Embedding) | Числовой вектор, представляющий смысл текста, изображения или другого объекта. Похожие по смыслу объекты обычно имеют близкие векторы. |
| Вектор | Упорядоченный набор чисел. В семантическом поиске он служит математическим представлением смысла текста. |
| Векторный индекс | Хранилище векторов и связанной информации, оптимизированное для быстрого поиска ближайших значений. |
| Семантический поиск | Поиск по смысловой близости, а не только по точному совпадению слов. |
| Косинусная близость (Cosine Similarity) | Мера сходства направлений двух векторов. Часто используется для сравнения эмбеддингов. |
| Ранжирование | Упорядочивание найденных фрагментов от наиболее релевантного к наименее релевантному. |
| `top_k` | Параметр, задающий количество лучших результатов, которые нужно вернуть из поиска. |
| Метаданные | Дополнительные сведения о фрагменте: путь к файлу, номера строк, тип документа, дата или автор. |
| Релевантность | Степень соответствия найденного материала текущему запросу. |
| Контекст поиска | Фрагменты, выбранные поисковой системой и добавленные в запрос модели. |
| Модель эмбеддингов | Модель, преобразующая текст в векторы. Индекс и запрос должны обрабатываться совместимыми моделями. |
| Векторная размерность | Количество чисел в одном эмбеддинге. Все сравниваемые векторы должны иметь одинаковую размерность. |

## Разработка программного обеспечения

| Термин | Понятное объяснение |
|---|---|
| Жизненный цикл ПО (Software Development Life Cycle, SDLC) | Этапы существования программной системы: анализ требований, проектирование, разработка, тестирование, выпуск, эксплуатация и сопровождение. |
| Требование | Описание того, что система должна делать или каким ограничением должна соответствовать. |
| Функциональное требование | Требование к поведению системы, например возможность создать заявку или вернуть товар. |
| Нефункциональное требование | Требование к качеству системы: производительности, безопасности, надёжности или удобству. |
| Критерий приёмки (Acceptance Criterion) | Проверяемое условие, по которому определяют, выполнена ли конкретная часть задачи. |
| Критерии готовности (Definition of Done) | Общий набор условий, после выполнения которых работа считается полностью завершённой. |
| Декомпозиция | Разбиение большой задачи на меньшие, понятные и проверяемые части. |
| Архитектура системы | Высокоуровневое устройство программы: основные компоненты, их ответственность, связи и потоки данных. |
| Компонент | Относительно самостоятельная часть системы с определённой ответственностью и интерфейсом. |
| Модуль | Файл или группа файлов, объединяющих связанную логику и предоставляющих понятный интерфейс. |
| Зависимость | Внешний пакет, сервис или другой модуль, без которого компонент не может работать. |
| Кодовая база (Codebase) | Совокупность исходного кода, тестов, конфигурации и документации проекта. |
| Репозиторий | Каталог проекта, история изменений которого обычно управляется системой контроля версий. |
| Система контроля версий | Инструмент для хранения истории файлов, сравнения изменений и совместной работы. |
| Git | Распределённая система контроля версий. Полная история репозитория обычно хранится на компьютере каждого участника. |
| Рабочее дерево (Working Tree) | Текущие файлы репозитория, которые пользователь видит и изменяет на диске. |
| Коммит (Commit) | Зафиксированный снимок изменений с автором, временем и описанием. |
| Ветка (Branch) | Независимая линия разработки, позволяющая работать над изменениями отдельно от основной версии. |
| Слияние (Merge) | Объединение изменений из разных веток. |
| Запрос на слияние (Pull Request, Merge Request) | Предложение включить изменения одной ветки в другую с обсуждением, проверками и review. |
| Разница изменений (Diff) | Построчное представление того, что добавлено, удалено или изменено между двумя версиями файлов. |
| Конфликт слияния | Ситуация, когда Git не может автоматически объединить несовместимые изменения и требуется решение человека. |
| `.gitignore` | Файл с правилами, какие файлы и каталоги Git не должен добавлять в историю. |
| Рефакторинг | Изменение внутренней структуры кода без намеренного изменения его внешнего поведения. |
| Технический долг | Накопленные упрощения и недостатки реализации, которые ускорили работу раньше, но усложняют изменения и поддержку сейчас. |
| Legacy-код | Унаследованный код, который продолжает использоваться, хотя может быть устаревшим, плохо документированным или сложным для изменения. |
| Обратная совместимость | Способность новой версии продолжать работать со старыми данными, интерфейсами или клиентами. |
| Миграция | Управляемый переход от старой структуры, версии или системы к новой. |
| Откат (Rollback) | Возврат к предыдущему стабильному состоянию после неудачного изменения или выпуска. |
| Развёртывание (Deployment) | Доставка и запуск новой версии приложения в целевой среде. |
| Production-среда | Реальная рабочая среда, в которой системой пользуются конечные пользователи. |
| Тестовая среда | Изолированная среда для проверки изменений без воздействия на реальных пользователей. |
| Конфигурация | Набор параметров, управляющих поведением приложения без изменения его исходного кода. |
| Переменная окружения (Environment Variable) | Именованное значение, которое операционная система или процесс передаёт приложению. Часто используется для путей и настроек. |
| Артефакт сборки | Результат процесса сборки: исполняемый файл, пакет, архив, отчёт или другой готовый к использованию объект. |

## Качество кода и тестирование

| Термин | Понятное объяснение |
|---|---|
| Тестовый сценарий (Test Case) | Описание входных данных, действий и ожидаемого результата для проверки конкретного поведения. |
| Unit-тест | Быстрый тест небольшой единицы логики, например одной функции, изолированной от внешних систем. |
| Интеграционный тест | Тест совместной работы нескольких компонентов, например сервиса и базы данных. |
| Сквозной тест (End-to-end, E2E) | Проверка полного пользовательского сценария через все основные слои системы. |
| Фикстура (Fixture) | Подготовленные данные или окружение, которые создаются перед тестом и при необходимости очищаются после него. |
| Mock-объект | Управляемая имитация зависимости, позволяющая проверить взаимодействие без реального внешнего сервиса. |
| Stub | Простая замена зависимости, возвращающая заранее заданный результат. |
| Утверждение (Assertion) | Проверка в тесте, что фактический результат соответствует ожидаемому условию. |
| Ожидаемый результат (Expected Result) | Поведение, которое должно произойти согласно требованиям. |
| Фактический результат (Actual Result) | Поведение, которое система действительно показала при проверке. |
| Позитивный сценарий | Проверка корректных входных данных и успешного результата. |
| Негативный сценарий | Проверка ошибочных, запрещённых или неполных данных и ожидаемой реакции системы. |
| Граничный случай (Edge Case) | Редкая или предельная ситуация: нулевое значение, максимальный размер, пустой список или граница срока. |
| Регрессионный тест | Тест, подтверждающий, что ранее исправленная ошибка или существующая функция не сломалась после изменений. |
| Покрытие тестами (Test Coverage) | Метрика того, какая часть кода была выполнена тестами. Высокое покрытие не гарантирует качество проверок. |
| Набор тестов (Test Suite) | Группа связанных тестов, запускаемых вместе. |
| Средство запуска тестов (Test Runner) | Программа, которая находит тесты, выполняет их и формирует отчёт. |
| `pytest` | Популярный Python-фреймворк для написания и запуска тестов с удобными фикстурами и расширениями. |
| `unittest` | Встроенный в Python фреймворк модульного тестирования. |
| Непрерывная интеграция (Continuous Integration, CI) | Автоматический запуск сборки, тестов и других проверок при изменении кода. |
| CI-конвейер (CI Pipeline) | Последовательность автоматических этапов: установка зависимостей, анализ, тестирование и подготовка артефактов. |
| Линтер (Linter) | Инструмент, находящий стилевые нарушения и некоторые типичные ошибки без запуска программы. |
| Статический анализ | Проверка исходного кода без выполнения, например анализ типов, зависимостей или потенциальных уязвимостей. |
| Code review | Проверка изменений другим разработчиком или агентом до включения в основную версию. |
| Замечание review | Конкретное описание проблемы с указанием места, влияния, доказательства и способа исправления. |
| Серьёзность дефекта (Severity) | Оценка влияния проблемы: от косметической до критической для безопасности или работоспособности. |
| Воспроизводимость | Возможность повторить тест, ошибку или эксперимент в тех же условиях и получить сопоставимый результат. |

## API, данные и серверная разработка

| Термин | Понятное объяснение |
|---|---|
| API (Application Programming Interface) | Согласованный способ взаимодействия программ друг с другом: набор операций, форматов данных и правил. |
| Публичный API | Часть интерфейса, предназначенная для использования другими модулями, приложениями или разработчиками. |
| Контракт API | Точное описание доступных операций, входных данных, ответов, ошибок и гарантий поведения. |
| REST | Архитектурный стиль веб-API, в котором ресурсы доступны по адресам, а действия выражаются стандартными HTTP-методами. |
| Endpoint | Конкретный адрес и HTTP-метод API, обрабатывающие определённую операцию. |
| HTTP | Протокол обмена запросами и ответами между клиентом и веб-сервером. |
| HTTP-метод | Тип операции запроса: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` и другие. |
| `GET` | HTTP-метод для получения данных без намеренного изменения ресурса. |
| `POST` | HTTP-метод, часто используемый для создания ресурса или запуска операции. |
| `PUT` | HTTP-метод полной замены представления ресурса по известному адресу. |
| `PATCH` | HTTP-метод частичного изменения ресурса. |
| `DELETE` | HTTP-метод удаления ресурса. |
| Код состояния HTTP | Числовой результат запроса: например, `200` означает успех, `404` - ресурс не найден, `500` - ошибка сервера. |
| Запрос (Request) | Сообщение клиента серверу, содержащее адрес, метод, заголовки и при необходимости данные. |
| Ответ (Response) | Сообщение сервера клиенту с кодом состояния, заголовками и данными результата. |
| Заголовок HTTP (Header) | Служебная информация запроса или ответа, например тип содержимого или данные авторизации. |
| Тело запроса (Body) | Основные данные, передаваемые в запросе, например JSON создаваемого объекта. |
| Query-параметр | Параметр после знака `?` в URL, обычно используемый для фильтрации, сортировки или пагинации. |
| Path-параметр | Переменная часть пути URL, например идентификатор объекта в `/orders/42`. |
| JSON | Текстовый формат представления объектов, списков, строк, чисел и логических значений. Часто используется в API. |
| JSON Schema | Формальное описание допустимой структуры JSON: полей, типов, обязательности и ограничений. |
| Сериализация | Преобразование объекта программы в формат для хранения или передачи, например в JSON. |
| Десериализация | Обратное преобразование данных из JSON или другого формата в объект программы. |
| Валидация | Проверка, что данные имеют правильный тип, структуру и допустимые значения. |
| Схема данных | Формальное описание полей, типов и связей данных. |
| CRUD | Четыре базовые операции с данными: создание, чтение, изменение и удаление. |
| Pydantic | Python-библиотека для описания моделей данных, валидации и сериализации на основе аннотаций типов. |
| Валидатор | Функция, проверяющая или преобразующая значение поля по заданному правилу. |
| Flask | Лёгкий Python-фреймворк для создания веб-приложений и API. |
| FastAPI | Python-фреймворк для API с аннотациями типов, автоматической валидацией и генерацией OpenAPI-документации. |
| База данных | Организованное хранилище данных, предоставляющее операции чтения и изменения. |
| SQL | Язык запросов к реляционным базам данных. |
| SQLite | Компактная реляционная база данных, работающая без отдельного серверного процесса. |
| Транзакция | Группа операций с базой данных, которая выполняется целиком или целиком отменяется. |
| Репозиторий данных (Repository Pattern) | Слой кода, скрывающий детали хранения и предоставляющий доменной логике понятные операции чтения и записи. |
| Сервисный слой (Service Layer) | Слой, содержащий бизнес-правила и координирующий работу моделей, репозиториев и внешних сервисов. |
| Идемпотентность | Свойство операции, при котором повторный одинаковый вызов не создаёт дополнительных нежелательных изменений. |
| `Decimal` | Тип Python для точной десятичной арифметики. Он предпочтительнее `float` для денежных расчётов. |
| Исключение (Exception) | Объект, сообщающий о ненормальной ситуации во время выполнения программы. |
| Обработка исключений | Перехват ожидаемых ошибок, их преобразование в понятный результат и безопасное завершение операции. |

## Безопасность

| Термин | Понятное объяснение |
|---|---|
| Принцип наименьших привилегий | Пользователь, процесс или агент получает только те права, которые необходимы для текущей задачи. |
| Песочница (Sandbox) | Изолированная среда, ограничивающая доступ программы к файлам, сети, процессам и другим ресурсам. |
| Граница доверия (Trust Boundary) | Место перехода данных между областями с разным уровнем доверия, где требуется дополнительная проверка. |
| Список разрешений (Allowlist) | Явный перечень разрешённых файлов, команд, адресов или операций. Всё остальное запрещается. |
| Список запретов (Denylist) | Перечень запрещённых значений или действий. Он обычно слабее allowlist, потому что невозможно заранее перечислить все опасные варианты. |
| Контроль доступа | Правила, определяющие, кто и какие действия может выполнять над ресурсом. |
| Аутентификация | Проверка личности пользователя или сервиса. Отвечает на вопрос: «Кто это?». |
| Авторизация | Проверка разрешений уже известного пользователя или сервиса. Отвечает на вопрос: «Что ему можно?». |
| Секрет | Конфиденциальное значение для доступа: пароль, закрытый ключ, токен или API-ключ. |
| API-ключ | Секретный идентификатор, позволяющий приложению обращаться к API от имени учётной записи или проекта. |
| Токен доступа (Access Token) | Ограниченное по правам и часто по времени значение для авторизованных запросов к сервису. Не следует путать с текстовым токеном языковой модели. |
| Утечка секрета | Попадание ключа, пароля или токена в код, журнал, сообщение, репозиторий или другое доступное посторонним место. |
| Инъекция промпта (Prompt Injection) | Попытка встроить в данные вредоносную инструкцию, чтобы модель нарушила исходные правила или выполнила опасное действие. |
| Jailbreak | Запрос или последовательность запросов, направленные на обход защитных ограничений модели. |
| Избыточная автономность (Excessive Agency) | Риск, возникающий, когда агенту предоставили больше инструментов, прав или самостоятельности, чем требуется задаче. |
| Обход пути (Path Traversal) | Атака, при которой специально сформированный путь, например с `..`, используется для доступа за пределы разрешённого каталога. |
| Безопасный корень (Safe Root) | Каталог, внутри которого программе разрешено читать или изменять файлы. Любой вычисленный путь проверяется относительно этого корня. |
| Проверка входных данных | Контроль типа, длины, формата и допустимого диапазона всех данных, поступивших извне. |
| Экранирование (Escaping) | Безопасное представление специальных символов, чтобы они считались данными, а не частью команды или разметки. |
| Командная инъекция | Уязвимость, при которой внешние данные превращаются в часть команды операционной системы. |
| `subprocess` | Модуль Python для запуска внешних программ. Безопаснее передавать команду списком аргументов и не использовать оболочку без необходимости. |
| Ограничение вывода | Максимальный объём данных, который разрешено читать из внешнего процесса или инструмента, чтобы избежать переполнения памяти и контекста. |
| Фиктивный секрет | Заведомо нерабочее учебное значение, похожее на ключ. Оно позволяет показать формат без риска реального доступа. |
| Аудит действий | Сохранение сведений о том, кто, когда и какое значимое действие выполнил. |
| Уязвимость зависимости | Ошибка безопасности во внешней библиотеке или пакете, используемом проектом. |

## Диагностика, процессы и эксплуатация

| Термин | Понятное объяснение |
|---|---|
| Процесс | Запущенный экземпляр программы со своей памятью, ресурсами и кодом завершения. |
| Асинхронность | Способ организации программы, при котором ожидание одной операции не блокирует выполнение других задач. |
| Очередь задач | Хранилище заданий, ожидающих обработки одним или несколькими исполнителями. |
| Планировщик задач | Компонент, запускающий действия по времени, расписанию или наступлению события. |
| Стандартный вывод (`stdout`) | Поток, в который программа записывает обычный результат работы. |
| Стандартный поток ошибок (`stderr`) | Поток для диагностических сообщений и ошибок программы. |
| Код завершения (Exit Code) | Число, возвращаемое процессом после окончания. Ноль обычно означает успех, ненулевое значение - ошибку. |
| Журналирование (Logging) | Запись диагностических событий приложения для анализа работы и ошибок. |
| Лог | Отдельная запись или файл с диагностическими событиями. |
| Уровень логирования | Важность сообщения: например `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`. |
| Структурированный лог | Запись в согласованном формате с отдельными полями, например временем, уровнем, `request_id` и типом события. |
| Временная метка (Timestamp) | Дата и время события в журнале. |
| Идентификатор запроса (`request_id`) | Уникальное значение, связывающее записи, относящиеся к одному запросу или операции. |
| Трассировка (Tracing) | Наблюдение за прохождением запроса через последовательность компонентов, инструментов или агентов. |
| Метрика | Числовой показатель работы системы, например число ошибок, время ответа или длина очереди. |
| Мониторинг | Автоматическое наблюдение за состоянием системы с помощью логов, метрик, проверок и оповещений. |
| Наблюдаемость (Observability) | Способность понять внутреннее состояние системы по её внешним сигналам: логам, метрикам и трассам. |
| Стек вызовов (Stack Trace) | Диагностический список функций и строк кода, через которые программа пришла к необработанной ошибке. |
| Ротация логов | Автоматическое создание новых файлов журнала и архивирование или удаление старых, чтобы они не росли бесконечно. |
| Срок хранения логов (Retention) | Период, в течение которого диагностические записи сохраняются до удаления. |
| Деградация с сохранением доступности | Поведение, при котором второстепенная функция отключается при ошибке, но основная возможность системы продолжает работать. |
| Дефект, баг (Bug) | Ошибка в программе, из-за которой фактическое поведение отличается от ожидаемого. |
| Воспроизведение ошибки | Повторение условий и шагов, стабильно вызывающих дефект. |
| Bug report | Краткий отчёт с условиями, шагами воспроизведения, ожидаемым и фактическим результатом. |
| Инцидент | Событие, нарушившее нормальную работу сервиса, безопасность или доступность данных. |
| Отчёт об инциденте | Документ с хронологией, влиянием, причиной, действиями по восстановлению и мерами предотвращения повторения. |
| Влияние инцидента (Impact) | Масштаб последствий: какие пользователи, данные, операции или сервисы пострадали. |
| Первопричина (Root Cause) | Основное условие, которое сделало инцидент возможным. Это не обязательно последняя ошибка в стеке. |
| Корректирующее действие | Мера, устраняющая обнаруженную причину или уже возникшее последствие. |
| Предупреждающее действие | Мера, уменьшающая вероятность или влияние похожего инцидента в будущем. |
| Постмортем (Postmortem) | Разбор инцидента после восстановления работы с акцентом на улучшение системы, а не на поиск виноватого. |

## Документация и файлы проекта

| Термин | Понятное объяснение |

| Reference-документация | Точное описание доступных функций, классов, параметров, ответов и ошибок. Её используют как справочник. |
| Учебник (Tutorial) | Пошаговый материал, который проводит новичка через практический результат и помогает приобрести навык. |
| Практическое руководство (How-to Guide) | Инструкция для решения конкретной задачи, предполагающая, что базовые знания уже есть. |
| Объяснение (Explanation) | Материал, раскрывающий причины, связи и принципы, а не только порядок действий. |
| Глоссарий | Список терминов предметной области с согласованными определениями. |
| Архитектурное решение (Architecture Decision Record, ADR) | Короткий документ, фиксирующий важное архитектурное решение, его контекст, варианты и последствия. |
| Модель C4 | Способ описания архитектуры через уровни: контекст системы, контейнеры, компоненты и код. |
| Документация API | Описание доступных операций API, данных, примеров, ошибок и правил использования. |
| Changelog | Упорядоченный список заметных изменений между версиями проекта. |
| Семантическое версионирование | Схема версий `MAJOR.MINOR.PATCH`, где части номера отражают несовместимые, совместимые функциональные и исправляющие изменения. |
| Манифест проекта | Файл с основными правилами, зависимостями, возможностями или метаданными проекта либо плагина. Точное назначение зависит от инструмента. |
| Файл инструкций агента | Текстовый файл с правилами работы в проекте: границами, командами проверки, стилем и архитектурными ограничениями. |
| Конфигурационный файл | Файл с настройками приложения или инструмента, отделёнными от программной логики. |
| `requirements.txt` | Распространённый файл со списком Python-зависимостей, которые устанавливаются через `pip`. |
| Виртуальное окружение Python | Изолированный каталог со своим интерпретатором и пакетами, позволяющий проектам использовать разные версии зависимостей. |
| Пакет Python | Устанавливаемая или импортируемая единица Python-кода, которая может содержать модули и подпакеты. |
| `pip` | Стандартный инструмент установки Python-пакетов из индекса или другого источника. |
| Кодировка UTF-8 | Универсальный способ хранения текста, поддерживающий русский язык и большинство письменностей мира. |
| Исходный путь | Путь к файлу, из которого взят материал или код. Он помогает проверить происхождение и актуальность информации. |
