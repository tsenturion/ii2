## Проверяем отсутствие конфликтующих context-файлов

Перед запуском ролей обязательно проверим, что наш `AGENTS.md` вообще имеет шанс загрузиться.

Hermes использует приоритет project context files. Более приоритетные `.hermes.md` или `AGENTS.override.md` могут перекрыть обычный `AGENTS.md`.

В корне выполняю:

Особенно смотрю, нет ли:

Если для этой учебной работы такие файлы уже существуют, я временно не использую их, потому что хочу проверить именно `AGENTS.md`.

Важно понимать причину. Если существует более приоритетный тип контекста, Hermes может показать обычный `AGENTS.md` как `shadowed`. Это не означает, что файл написан неправильно. Это означает, что он уступил приоритет другому context file.


файл не был принят системой безопасности.

Если файл слишком большой, Hermes может отметить его как truncated.

Таким образом, «я создал AGENTS.md» и «Hermes использует AGENTS.md» — это две разные вещи.

## Что будет, если создать .hermes.md

Покажу важный принцип, но специально не оставляю такой файл в проекте.

Hermes использует приоритет project context types. `.hermes.md` или `HERMES.md` находится выше обычного `AGENTS.md`. Поэтому наличие такого файла может изменить то, какой тип проектного контекста будет активен.

Именно поэтому при отладке неожиданного поведения я первым делом смотрю:

```text
/context
```

а не пытаюсь угадывать, почему агент «не слушается» нашего `AGENTS.md`.

## Почему после изменения AGENTS.md лучше открыть новую сессию

Если я существенно изменил корневой `AGENTS.md`, для чистой проверки я создаю новую сессию.

Hermes загружает основной project context при старте сессии. Вложенные `AGENTS.md` также могут обнаруживаться постепенно, когда агент начинает обращаться к соответствующим подкаталогам.

Поэтому после серьёзного изменения роли я нажимаю:

```text
Ctrl + N
```

и создаю новую сессию внутри соответствующего Project.

Это избавляет нас от ситуации, когда мы пытаемся проверять новую конфигурацию внутри длинного диалога, который уже содержит старые инструкции.

## Проверяем размер контекста

Теперь в любой из ролевых сессий выполняю:

```text
/context all
```

Здесь можно увидеть более подробное распределение контекстного окна.

Это полезно потому, что `AGENTS.md` добавляется в контекст агента. Чем больше мы превращаем его в огромную методичку, тем больше токенов будет постоянно занимать проектная инструкция.

Hermes рекомендует держать project context компактным. Файлы имеют ограничения по размеру, а слишком крупный файл может быть обрезан.

Поэтому `AGENTS.md` должен содержать устойчивые правила проекта, а не всю документацию компании.

## Проверяем Git

В завершение открываю Terminal в корне проекта:

```powershell
Set-Location "C:\ai-course\hermes-multiagent"
```

Выполняю:

```powershell
git status --short
```

Я проверяю, какие файлы появились.

У нас должны быть как минимум:

```text
AGENTS.md
roles/migrator/AGENTS.md
roles/reviewer/AGENTS.md
validation/legacy_model.py
```

После этого смотрю:

```powershell
git diff
```

Теперь я могу отдельно увидеть конфигурационные инструкции и изменение, которое выполнял Migrator.

Если всё соответствует практической работе, фиксирую результат:

```powershell
git add AGENTS.md roles validation
```

Затем:

```powershell
git commit -m "Add Migrator and Reviewer agent contexts"
```

## Что мы фактически проверили

В этой работе я не ограничился созданием двух Markdown-файлов.

Сначала мы сформировали общий контекст проекта. Затем создали отдельные роли Migrator и Reviewer. После этого для каждой роли запустили отдельную Hermes-сессию с собственной рабочей директорией.

Командой `/status` мы проверили, откуда работает агент.

Командой `/context` мы проверили, какие `AGENTS.md` действительно попали в его контекст.

Migrator получил разрешённую миграционную задачу и смог изменить код, но должен был отказаться от действий за пределами роли.

Reviewer получил существующий diff, но даже при прямом запросе «исправь ошибку» должен был остаться в режиме проверки и не модифицировать файлы.

Именно такая проверка гораздо полезнее, чем просто открыть `AGENTS.md` и убедиться, что в нём нет опечаток.

У `AGENTS.md` нет строгой схемы, которая автоматически сообщит нам: «роль настроена правильно». Поэтому валидность агентной конфигурации мы проверяем на трёх уровнях: правильное обнаружение файла, правильный контекст и правильное фактическое поведение.

При этом я отдельно помню, что `AGENTS.md` является инструкцией для модели, а не жёсткой системой безопасности. Если действие действительно опасно, одного текста «не делай это» недостаточно. Технические ограничения инструментов, approvals, sandbox и права доступа должны дополнять текстовые правила.
