## Что мы будем делать

Сейчас мы соберём настоящую мультиагентную цепочку в Hermes. У нас будет небольшой Python-проект, использующий Pydantic первой версии. Наша задача будет заключаться в обновлении зависимости до Pydantic 2 и адаптации существующего кода.

Но главное здесь не сама миграция Pydantic. Если бы нам нужно было просто обновить несколько строк, один агент справился бы с этим без проблем. Нам важно специально разделить работу между тремя исполнителями.

Первый субагент будет Planner. Он получит проект, изучит его и составит план миграции, но ничего менять не будет. Второй субагент будет Coder. Он получит исходную задачу вместе с результатом Planner, внесёт изменения и запустит проверки. Третий субагент будет Reviewer. Он начнёт работу с отдельным контекстом, посмотрит уже изменённый проект и независимо проверит результат.

Это действительно разные экземпляры агентов, а не просто три ответа одного чата. Hermes создаёт субагентов через `delegate_task`; каждый дочерний агент получает собственный контекст и отдельную терминальную сессию, а основному агенту возвращается итог его работы. История разговора родителя автоматически дочернему агенту не передаётся, поэтому контекст для каждого этапа необходимо формировать явно.

```text
import unittest

from pydantic import ValidationError

from services import serialize_user


class UserServiceTests(unittest.TestCase):

    def test_valid_user(self):
        data = {
            "name": "Анна",
            "email": "anna@example.com",
            "age": 25
        }

        self.assertEqual(serialize_user(data), data)

    def test_minor_user_rejected(self):
        data = {
            "name": "Иван",
            "email": "ivan@example.com",
            "age": 16
        }

        with self.assertRaises(ValidationError):
            serialize_user(data)


if __name__ == "__main__":
    unittest.main()
```

Теперь я смотрю на итоговое сообщение Planner.

Он должен заметить, что в `requirements.txt` используется ветка Pydantic 1.

В `models.py` он должен обнаружить старый механизм `validator`.

Он должен связать эти места с миграцией на API второй версии.

Но сейчас мы ничего из этого вручную не исправляем.

Мне здесь важно показать сам принцип передачи работы между агентами.

Planner завершил работу и вернул итог основному агенту. Теперь этот результат должен стать частью контекста следующего субагента.

Поскольку Coder начнёт с чистого контекста, фраза «сделай то, что предложил Planner» сама по себе плохая. Coder не знает историю Planner автоматически. Родитель должен явно передать ему план, путь к проекту, требования и способ проверки. Это базовое правило делегирования в Hermes.

```text
проверить, что не выполнен лишний рефакторинг;

```

Теперь снова нажимаю на панель `Subagents`.

Открываю Reviewer.

Здесь мне особенно важно, чтобы это действительно был новый дочерний агент.

Reviewer не должен продолжать рассуждение Coder. Он получает свежий контекст и смотрит на результат со стороны.

Это одна из причин, почему отдельный субагент подходит для review: Hermes изолирует его историю от предыдущего исполнителя, а значит Reviewer не обязан защищать решения, которые сам же ранее принимал. Механизм `/review` в Hermes построен на похожей идее отдельного reviewer-субагента, но в этой лабораторной мы сознательно используем обычный `delegate_task`, чтобы явно построить именно цепочку Planner → Coder → Reviewer.

## Что должно произойти на этапе Reviewer

Я ожидаю от Reviewer не просто сообщение «код хороший».

Он должен проверить реальные файлы.

Он должен посмотреть Git diff.

Он должен выполнить тесты.

Он должен проверить версию установленной библиотеки.

И только после этого сформировать итог.

Если Reviewer сообщает:

```text
PASS
```

мы смотрим, на каких доказательствах это основано.

Если он сообщает:

```text
FAIL
```

мы также не исправляем проблему автоматически. Для текущей практики это важный результат: независимый reviewer нашёл недостаток после работы coder.

Если бы мы строили более сложную агентную систему, после `FAIL` можно было бы организовать дополнительный цикл Reviewer → Coder → Reviewer. Но это уже другая архитектура. Сейчас наша цепочка заканчивается на первом независимом review.

Reviewer не должен создавать дополнительные изменения.

Если после Reviewer появляются новые правки исходного кода, значит мы неправильно сформулировали его роль или он вышел за установленные ограничения.

Это хороший пример того, зачем в мультиагентных системах недостаточно просто дать агенту имя `Reviewer`. Роль должна определяться не названием, а конкретными разрешёнными и запрещёнными действиями.

## Проверяем дерево субагентов в Hermes

Теперь я хочу посмотреть цепочку целиком.

В чате Hermes ввожу:

```text
/agents
```

Команда `/agents`, она же `/tasks`, открывает представление активных и завершённых субагентов. В Hermes здесь можно просматривать структуру делегирования, состояние дочерних агентов и историю их работы.

Я хочу увидеть три разных выполнения.

Planner.

Coder.

Reviewer.

Если вместо этого вся работа была сделана основным агентом, наша учебная задача фактически не выполнена.

Если Coder и Reviewer запускались одновременно, цепочка также построена неправильно. Reviewer должен получать уже готовый результат Coder.

Если Planner и Coder запускались одновременно, Coder не мог использовать итоговый план Planner.

Поэтому в этой задаче последовательность принципиальна.

## Теперь автоматизируем всю цепочку

До этого момента я специально запускал три этапа отдельными командами. Это нужно было для того, чтобы мы увидели механику.

Теперь можно показать, как ту же цепочку передать основному агенту как единую цель.

Перед повторным экспериментом я сначала возвращаю проект к baseline.

В Terminal выполняю:

```powershell
git restore .
```

Проверяю:

```powershell
git status --short
```

Рабочее дерево снова должно быть чистым.

Возвращаю старую зависимость в виртуальное окружение:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Теперь в чат отправляю единый оркестрационный запрос.

```text
/goal Выполни учебную миграцию проекта, путь которого передан как значение переменной $projectRoot, строго через последовательную мультиагентную цепочку Planner → Coder → Reviewer.

Основной агент является только координатором и не должен самостоятельно изменять исходные файлы.

Для каждого этапа обязательно создавай новый отдельный leaf-субагент через delegate_task.

Этап 1 — Planner.

Передай Planner путь проекта и TASK.md.

Planner должен изучить проект, составить план миграции и определить проверки.

Planner не имеет права изменять файлы.

Дождись завершения Planner и получи его итоговый результат.

Только после этого переходи к следующему этапу.


Этап 2 — Coder.

Создай нового субагента.

Передай ему путь проекта, TASK.md и итоговый план Planner.

Coder должен обновить зависимость с Pydantic 1.x до Pydantic 2.x, адаптировать код, установить обновлённые зависимости и выполнить проверки.

Команда тестов:

.\.venv\Scripts\python.exe -m unittest discover -s tests -v

Coder должен вернуть перечень изменений и результаты проверок.

Дождись полного завершения Coder.

Только после этого запускай следующий этап.


Этап 3 — Reviewer.

Создай нового независимого субагента.

Передай ему путь проекта, исходные требования и информацию о baseline в Git.

Не передавай ему рассуждения Coder как истину.

Reviewer должен самостоятельно изучить git diff, проверить миграцию, версию Pydantic, тесты и запуск main.py.

Reviewer не имеет права изменять файлы.

Reviewer должен вернуть PASS или FAIL и конкретные замечания.


Не запускай Planner, Coder и Reviewer параллельно.

Не заменяй какой-либо этап собственной работой основного агента.

После завершения всех трёх субагентов сформируй только итоговую сводку:

что решил Planner;
что изменил Coder;
что проверил Reviewer;
финальный статус Reviewer.

Даже если Reviewer вернёт FAIL, автоматически проблему не исправляй. На этом цепочка должна завершиться.
```

Здесь мы используем `/goal` не вместо multi-agent механизма, а для оркестрации процесса между несколькими ходами. В Hermes постоянная цель сохраняется между ходами, а после каждого ответа система проверяет, достигнута ли она; если нет, Hermes может автоматически продолжить работу без нашего сообщения «продолжай».

То есть `/goal` поддерживает жизнь всей цепочки, а `delegate_task` создаёт собственно исполнителей.

Это две разные функции.

## Наблюдаем автоматическую цепочку

После отправки большого запроса я не переключаюсь сразу на что-то другое.

Смотрю на `Subagents`.

Сначала должен появиться Planner.

Пока Planner не завершился, Coder появляться не должен.

После Planner должен появиться Coder.

После завершения Coder должен появиться Reviewer.

Если я вижу одновременно три активных субагента, значит основной агент не выполнил наше требование о последовательности.

Для этой задачи это ошибка архитектуры, даже если итоговый код окажется правильным.

Мы специально изучаем зависимости между этапами.

Planner создаёт результат, необходимый Coder.

Coder создаёт результат, необходимый Reviewer.

Поэтому здесь синхронная последовательность важнее потенциального выигрыша от параллельного запуска.

## Что смотрим в отчёте Planner

Теперь мы разбираем полученные результаты уже не как ответы нейросети, а как результаты отдельных ролей.

У Planner я проверяю, нашёл ли он все места, связанные с Pydantic v1.

Мне важно, чтобы его план был привязан к конкретным файлам.

Формулировка вроде:

```text
Нужно обновить код под новую версию.
```

практически бесполезна.

Хороший план должен позволять следующему агенту понять область работы без повторного полного исследования задачи.

## Что смотрим в отчёте Coder

У Coder я проверяю не красоту объяснения, а реальные изменения.

Открываю:

```powershell
git diff
```

Проверяю, соответствует ли diff задаче.

Если изменилось двадцать несвязанных файлов, задаю вопрос: почему?

Если Coder изменил только необходимые участки, это хороший признак.

После этого снова выполняю:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

И:

```powershell
.\.venv\Scripts\python.exe main.py
```

## Что смотрим в отчёте Reviewer

Здесь самый важный вопрос звучит так: проверил ли Reviewer результат или просто пересказал изменения?

Фразы:

```text
Изменения выглядят корректно.
```

недостаточно.

Я хочу видеть, что Reviewer действительно выполнил команды проверки.

Он должен самостоятельно подтвердить версию библиотеки.

Он должен посмотреть diff.

Он должен прогнать тесты.

Только после этого его `PASS` приобретает смысл.

## Финальная фиксация результата

Если Reviewer вернул `PASS`, я могу зафиксировать миграцию.

В Terminal выполняю:

```powershell
git add .
```

Затем:

```powershell
git commit -m "Migrate project to Pydantic v2"
```

Проверяю:

```powershell
git status
```

В конце рабочее дерево должно быть чистым.

Теперь у нас существует понятная история:

```text
Baseline: Pydantic v1
```

и затем:

```text
Migrate project to Pydantic v2
```

Это позволяет показать студентам, что агентная работа происходит внутри обычного процесса разработки, а не существует отдельно от Git, тестов и проекта.

## Что именно мы собрали

В результате этой практики у нас появился основной Hermes Agent, который выполняет роль координатора.

Planner получает свежий контекст, анализирует исходное состояние и возвращает план.

Coder получает задачу вместе с планом и выполняет фактическую миграцию.

Reviewer начинает отдельную проверку уже изменённого проекта и возвращает независимое заключение.

Главный агент связывает эти результаты между собой, но не обязан самостоятельно выполнять работу каждого исполнителя.

Именно здесь мы практически видим отличие single-agent режима от multi-agent. Если бы мы передали обычному агенту запрос «обнови Pydantic и проверь результат», возможно, он решил бы задачу быстрее. Но мы не увидели бы разделения ответственности и независимого контекста.

В нашей схеме специально появляется граница между планированием, реализацией и проверкой. Это и есть основная учебная ценность цепочки Planner → Coder → Reviewer.
