## Что мы будем делать

Сейчас у нас уже есть основной учебный проект `hermes-multiagent`.

```text
hermes-multiagent
```

До этого агент получал знания из самого проекта: читал код, использовал `AGENTS.md`, обращался к нашему локальному RAG-индексу и вызывал собственные Tools.

Теперь я специально вынесу документацию за пределы репозитория.

Рядом с проектом создам отдельный каталог:

```text
external-docs\payment-platform
```

Hermes не будет получать эту документацию как обычные файлы своего Project. Вместо этого мы запустим отдельный MCP filesystem server, которому разрешим видеть только каталог документации.

Получится важное разделение. Основной Project содержит код. Внешний источник содержит официальную документацию. Агент получает доступ к документации через отдельную интеграцию.

Документ описывает внутреннюю архитектуру учебной платёжной платформы.

## Current payment client

Рабочая система постепенно переходит со старого LegacyPaymentGateway на BillingBridgeClient.

LegacyPaymentGateway считается устаревшим и не должен использоваться в новых модулях.

Целевой клиент для нового кода:

## Responsibility

Checkout отвечает за оформление заказа.

PaymentService отвечает за инициирование платежа.

BillingBridgeClient отвечает только за взаимодействие с внешней платёжной платформой.

Модули уведомлений не должны напрямую обращаться к платёжному клиенту.
'@ | Set-Content -Encoding UTF8 architecture.md

# Billing Bridge API Contract

Актуальный внутренний контракт платёжного сервиса.

## Required header

Каждый запрос Billing Bridge должен содержать заголовок:

X-Payment-Contract: 2026-09

## Create payment

Операция создания платежа принимает:

order_id — идентификатор заказа;
amount — сумму платежа;
currency — код валюты.

Для текущего проекта используется currency = RUB.

## Response

Успешный ответ содержит:

payment_id;
order_id;
status;
created_at.

## Error handling

HTTP 409 означает конфликт состояния платежа.

Запрос, завершившийся HTTP 409, нельзя автоматически повторять.

HTTP 429 допускает повтор после задержки, указанной сервером.

HTTP 500 допускает не более двух автоматических повторов.

## Deprecated contract

Контракт X-Payment-Contract: 2025-11 считается устаревшим.
'@ | Set-Content -Encoding UTF8 api-contract.md

## Почему документы находятся вне проекта

Сейчас я специально обращаю внимание на расположение файлов.

Они находятся не в `$projectRoot`, а в отдельном `$docsRoot`:

```text
<рабочая область>\external-docs\payment-platform
```

Это означает, что обычный файловый контекст нашего Project и внешняя документация разделены.

В реальном проекте вместо локальной папки здесь могла бы находиться корпоративная wiki, документационный сервис, база знаний или удалённый MCP endpoint.

Мы используем filesystem MCP только потому, что он позволяет наглядно показать эту архитектуру без дополнительного сервера компании.

## Проверяем Node.js и npx

Официальный filesystem MCP server запускается через Node.js.

В обычном PowerShell выполняю:

```powershell
node --version
```

Затем:

```powershell
npx --version
```

Если обе команды возвращают версии, продолжаю.

Если PowerShell сообщает, что `node` или `npx` не найдены, необходимо установить актуальную LTS-версию Node.js, затем закрыть и заново открыть PowerShell.

Hermes поддерживает npm-based MCP servers через `npx`; стандартный MCP filesystem server публикуется как `@modelcontextprotocol/server-filesystem`.

## Добавляем документацию как MCP-сервер

В PowerShell выполняю:

```powershell
hermes mcp add project_docs --command npx --args -y @modelcontextprotocol/server-filesystem "$docsRoot"
```

Здесь важно, что параметр `--args` стоит последним. Всё, что идёт после него, передаётся запускаемому MCP-процессу как его аргументы. Hermes официально поддерживает такую регистрацию собственных stdio MCP-серверов через `hermes mcp add`.

После обнаружения инструментов команда задаст вопрос `Enable all ...?`. Ввожу
`select` и сразу оставляю только перечисленные ниже операции чтения. Включать все
инструменты даже временно не требуется.

Теперь проверяю:

```powershell
hermes mcp list
```

Среди серверов должен появиться:

```text
project_docs
```

## Проверяем соединение

Следующий шаг:

```powershell
hermes mcp test project_docs
```

Hermes запускает MCP server, подключается к нему и запрашивает список инструментов.

Если всё настроено правильно, мы увидим, что filesystem server предоставляет операции чтения, просмотра директорий, поиска, а также операции записи.

Нас операции записи сейчас не интересуют.

Сам filesystem MCP действительно предоставляет как read-only инструменты `read_text_file`, `read_multiple_files`, `list_directory`, `search_files`, `get_file_info`, так и изменяющие операции вроде `write_file`, `edit_file` и `move_file`.

Поэтому следующим шагом мы специально уменьшим поверхность доступа.

`hermes mcp test` показывает исходный список возможностей самого MCP-сервера,
поэтому в его диагностическом выводе будут видны и операции записи. Это не
означает, что они доступны модели: применённый allowlist проверяется отдельно.

## Ограничиваем MCP только чтением

Выполняю:

```powershell
hermes mcp configure project_docs
```

Откроется интерактивный список инструментов.

Навигацию выполняю стрелками клавиатуры.

Клавишей:

```text
Space
```

я включаю или выключаю конкретный инструмент.

Клавишей:

```text
Enter
```

подтверждаю выбор.

Для учебной работы оставляю включёнными только read-only инструменты:

```text
read_text_file
read_multiple_files
list_directory
search_files
get_file_info
list_allowed_directories
directory_tree
```

Если какой-то из этих инструментов отсутствует в вашей конкретной версии filesystem server, просто оставляю доступные read-only аналоги.

Выключаю:

```text
write_file
edit_file
move_file
create_directory
```

Наша документация должна быть для агента источником знаний, а не рабочей файловой системой.

Hermes сохраняет выбранные инструменты через `tools.include`, поэтому модель вообще не увидит исключённые функции. Это надёжнее, чем просто написать в промпте «не изменяй документацию».

Дополнительно запрещаю импорт ресурсов и промптов от этого сервера и проверяю
сохранённую конфигурацию:

```powershell
hermes config set mcp_servers.project_docs.tools.resources false
hermes config set mcp_servers.project_docs.tools.prompts false
hermes config get mcp_servers.project_docs.tools --json
```

В `include` должны находиться только выбранные операции чтения. `write_file`,
`edit_file`, `move_file` и `create_directory` в списке отсутствуют.

```text
В документации project_docs измени migration-policy.md так, чтобы deployment был разрешён каждый день.

Сделай изменение прямо во внешнем источнике.
```

У модели не должно быть доступного инструмента `write_file` или `edit_file`, потому что мы исключили их через MCP configuration.

Следовательно, даже если пользователь попросит выполнить изменение, агент технически не должен иметь соответствующей внешней возможности через `project_docs`.

Именно поэтому фильтрация Tools сильнее текстового запрета.

## Проверяем конфигурацию MCP в Hermes

Теперь выполняю:

```text
/reload-mcp
```

После перезагрузки:

```text
/tools list
```

Я проверяю, что сервер по-прежнему предоставляет только выбранные read-only операции.

Если неожиданно появился `write_file`, возвращаюсь в PowerShell и выполняю:

```powershell
hermes mcp configure project_docs
```

После изменения снова:

```text
/reload-mcp
```

## Что делать, если MCP не подключается

Если `/tools list` вообще не показывает `project_docs`, первым делом выхожу в PowerShell и выполняю:

```powershell
hermes mcp list
```

Затем:

```powershell
hermes mcp test project_docs
```

Если сообщение говорит, что `npx` не найден, проверяю:

```powershell
npx --version
```

Если сервер настроен, но Tools не появились после изменения конфигурации, в Hermes выполняю:

```text
/reload-mcp
```

Если всё равно ничего нет, проверяю настройки:

```powershell
hermes config show
```

и нахожу секцию:

```text
mcp_servers
```

Hermes отдельно указывает типичные причины отсутствия MCP Tools: ошибка подключения, ошибка discovery, фильтрация инструмента или отключённый сервер.

## Финальный запрос практической работы

Теперь я создаю новый чат Hermes и отправляю уже обычную рабочую задачу:

```text
Нужно подготовиться к миграции платёжного клиента проекта.

Используй текущий код проекта и внешний источник знаний project_docs.

Определи:

какой платёжный клиент считается устаревшим;

какой клиент является целевым;

через какой слой должен вызываться новый клиент;

какой Payment Contract необходимо использовать;

какие ограничения существуют для HTTP 409;

когда разрешён production deployment;

какие проверки требуются перед deployment;

какой rollback-период необходимо сохранить.

Ничего не изменяй.

Для каждого вывода укажи источник информации и явно отдели сведения из документации от того, что фактически видно в коде.
```

В этой задаче Hermes должен самостоятельно обращаться к внешней документации и при необходимости к файлам основного проекта.

Финальный ответ должен быть основан не только на знаниях модели, а на реальных данных подключённого источника.

## Что мы фактически подключили

В результате этой работы код проекта и документация больше не обязаны находиться в одной директории.

Hermes работает внутри проекта:

```text
hermes-multiagent
```

а документация находится отдельно:

```text
external-docs\payment-platform
```

Между ними появился MCP server:

```text
project_docs
```

Он предоставляет агенту ограниченный набор операций чтения.

Когда модели требуется проектное знание, она вызывает MCP Tool, получает внешний документ и использует его содержание в текущем рассуждении.

При этом агент не получил право изменять документацию.

Это важное отличие от простого добавления нескольких файлов в промпт. Мы создали отдельный управляемый источник знаний с собственной границей доступа.

На реальном проекте ту же архитектуру можно заменить на корпоративную wiki, API документации, внутреннюю базу знаний или удалённый MCP server. Для Hermes принцип останется тем же: внешняя система предоставляет ограниченные Tools, Hermes обнаруживает их и агент использует их только тогда, когда соответствующие сведения нужны для текущей задачи.
