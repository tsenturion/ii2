## Создаём GitHub Actions workflow

Теперь на основной ветке заранее создадим CI.

В центральном чате Hermes отправляю:

```text
Создай файл:

.github/workflows/ci.yml

со следующим содержимым.

Другие файлы не изменяй.
```

Содержимое:

```yaml
name: CI

on:
  pull_request:
    branches:
      - main

jobs:
  tests:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      - name: Run tests
        run: python -m unittest discover -s ci_lab/tests -v
```

Здесь ключевая часть:

```yaml
on:
  pull_request:
```

означает, что workflow будет реагировать на события Pull Request.

GitHub рекомендует для Python workflows использовать `actions/checkout`, `actions/setup-python` и затем запускать обычную команду тестирования проекта.

## Hermes проверяет CI

После создания PR в нашем первоначальном промпте уже было требование получить checks.

Hermes должен вызвать:

```text
gh pr checks
```

Если номер PR известен, может использовать:

```text
gh pr checks <номер>
```

Команда `gh pr checks` специально показывает CI-состояние одного Pull Request. Она различает состояния `pass`, `fail`, `pending`, `skipping` и `cancel`. Если аргумент не передан, CLI использует PR текущей ветки.

Если CI ещё выполняется, правильный ответ агента должен быть примерно:

```text
CI: pending
```

а не:

```text
CI успешно пройден.
```

## Просим Hermes дождаться завершения checks

Если в первом ответе CI ещё находится в состоянии pending, отправляю следующее сообщение:

```text
Продолжи работу с тем же Pull Request.

Не изменяй код.

Отслеживай CI до завершения через GitHub CLI.

После завершения сообщи фактический результат checks.

PR не объединяй.
```

Hermes может использовать:

```text
gh pr checks --watch
```

Эта команда остаётся активной до завершения проверок. По умолчанию состояние обновляется каждые 10 секунд; также поддерживается `--fail-fast`.

После завершения я ожидаю один из двух реальных результатов:

```text
pass
```

или:

```text
fail
```

## Просим Hermes исследовать причину CI failure

Отправляю:

```text
CI текущего Pull Request завершился ошибкой.

Используя GitHub CLI, определи, какая серверная проверка упала и почему.

Ничего пока не исправляй.

Сообщи фактическую причину на основании GitHub Actions.
```

В зависимости от выбранной стратегии Hermes может использовать `gh pr checks`, затем перейти к конкретному Actions run.

Для списка запусков существует:

```text
gh run list
```

А `gh run watch` позволяет наблюдать конкретный workflow run до завершения. Для runs, связанных с PR, сама документация GitHub CLI рекомендует прежде всего использовать `gh pr checks`.

## Открываем лог ошибки

В браузере захожу:

```text
Pull Request
```

затем:

```text
Checks
```

далее:

```text
Details
```

Открываю job:

```text
tests
```

и step:

```text
Run tests
```

В журнале должен быть assertion failure с различием между:

```text
alice_smith
```

и:

```text
alice-smith
```

Теперь мы видим, что CI является не просто меткой success/fail, а внешним источником диагностической информации для агента.

## Исправляем PR через Hermes

Теперь отправляю:

```text
Исправь только намеренно сломанный тест текущего Pull Request.

После изменения:

запусти тесты локально;

проверь git diff;

создай новый commit;

push в существующую ветку;

не создавай новый Pull Request;

после push дождись нового CI;

сообщи итоговый статус GitHub checks.

Не выполняй merge.
```

Hermes должен продолжить работать с уже существующим PR.

После push GitHub автоматически запускает очередной CI run.

Когда он завершится, агент снова должен использовать:

```text
gh pr checks
```

и получить `pass`.

## Проверяем историю PR

На GitHub открываю наш Pull Request.

Нажимаю вкладку:

```text
Commits
```

Я должен увидеть несколько commits: исходное изменение, специально сломанный вариант и последующее исправление.

Возвращаюсь на:

```text
Conversation
```

Checks должны быть зелёными после последнего исправления.

## Проверяем, что Hermes не выполнил merge

В Terminal выполняю:

```powershell
gh pr view --json state,mergedAt,mergeStateStatus,url
```

PR должен оставаться открытым, а:

```text
mergedAt
```

не должен содержать дату слияния.

Это важная граница нашей практики.

Создать PR и проверить CI агенту разрешено.

## Почему мы не заканчиваем после gh pr create

Теперь я фиксирую основную идею занятия.

Команда:

```text
gh pr create
```

говорит только о том, что объект Pull Request успешно создан на GitHub. Она ничего не доказывает о качестве кода.

Даже успешный локальный тест не подтверждает серверный CI.

И только:

```text
gh pr checks
```

даёт агенту текущее состояние проверок GitHub.

Это соответствует дисциплине встроенного GitHub Skill Hermes: удалённое состояние необходимо читать свежим запросом, а не выводить из локального состояния или прошлого сообщения.

## Что мы фактически сделали

В этой практике Hermes начал работу с локального Git-репозитория, но закончил уже внутри реального GitHub-процесса.

Сначала на `main` существовал CI workflow.

После этого агент создал отдельную feature-ветку.

Он изменил код и тест.

Локально проверил результат.

Создал commit.

Отправил ветку на GitHub.

Через `gh pr create` создал Pull Request. GitHub CLI официально поддерживает создание PR с указанием base/head, title и body.

Событие Pull Request запустило GitHub Actions.

После этого Hermes отдельно запросил серверное состояние через `gh pr checks`.

Мы увидели как успешный, так и неуспешный CI и проверили, что после дополнительного push существующий Pull Request обновляется автоматически.

В результате агент здесь уже работает не просто с кодом. Он становится участником полноценного процесса разработки: локальный Git, удалённая ветка, GitHub Pull Request и внешний CI образуют единый рабочий цикл.
