## Создаём GitHub Actions workflow

Workflow GitHub Actions всегда находится в `.github/workflows` относительно
корня Git-репозитория. В нашей структуре учебный Python-проект вложен в общий
репозиторий, поэтому сам workflow находится рядом с каталогом
`hermes-multiagent`, а команда тестирования получает явную рабочую директорию.

В центральном чате Hermes отправляю:

```text
Создай файл:

.github/workflows/ci.yml

со следующим содержимым.

Другие файлы не изменяй.
```

Содержимое:

```yaml
name: CI

on:
  pull_request:
    branches:
      - main

permissions:
  contents: read

jobs:
  tests:
    runs-on: ubuntu-latest

    defaults:
      run:
        working-directory: hermes-multiagent

    steps:
      - name: Получить исходный код
        uses: actions/checkout@v7

      - name: Настроить Python
        uses: actions/setup-python@v7
        with:
          python-version: "3.13"

      - name: Запустить тесты CI-практики
        run: python -m unittest discover -s ci_lab/tests -v
```

Здесь ключевая часть:

```yaml
on:
  pull_request:
```

означает, что workflow будет реагировать на события Pull Request.

GitHub рекомендует для Python workflows использовать `actions/checkout`, `actions/setup-python` и затем запускать обычную команду тестирования проекта.

## Hermes проверяет CI

После создания PR в нашем первоначальном промпте уже было требование получить checks.

Hermes должен вызвать:

```text
gh pr checks
```

Если номер PR известен, может использовать:

```text
gh pr checks <номер>
```

Команда `gh pr checks` специально показывает CI-состояние одного Pull Request. Она различает состояния `pass`, `fail`, `pending`, `skipping` и `cancel`. Если аргумент не передан, CLI использует PR текущей ветки.

Если CI ещё выполняется, правильный ответ агента должен быть примерно:

```text
CI: pending
```

а не:

```text
CI успешно пройден.
```

## Просим Hermes дождаться завершения checks

Если в первом ответе CI ещё находится в состоянии pending, отправляю следующее сообщение:

```text
Продолжи работу с тем же Pull Request.

Не изменяй код.

Отслеживай CI до завершения через GitHub CLI.

После завершения сообщи фактический результат checks.
```

Hermes может использовать:

```text
gh pr checks --watch
```

Эта команда остаётся активной до завершения проверок. По умолчанию состояние обновляется каждые 10 секунд; также поддерживается `--fail-fast`.

После завершения я ожидаю один из двух реальных результатов:

```text
pass
```

или:

```text
fail
```

```text
В текущем Pull Request специально измени ожидаемое значение нового теста так,
чтобы тест гарантированно падал. Например, ожидай alice-smith вместо
alice_smith.

Запусти тест локально и зафиксируй фактическое падение. Затем сохрани изменение
в истории рабочей ветки и отправь её в удалённый репозиторий. После обновления
Pull Request дождись результата нового CI и сообщи его, пока не исправляя
причину.
```

После обновления ветки GitHub автоматически запускает workflow повторно.

## Исследуем серверную причину ошибки

Проверяю состояние:

```powershell
gh pr checks --watch
```

CI должен завершиться ошибкой. Затем поручаю Hermes получить доказательства с
GitHub, а не выводить причину только из локального запуска:

```text
CI текущего Pull Request завершился ошибкой.

Используя GitHub CLI, определи, какая серверная проверка упала и почему. Покажи
фактическую причину на основании GitHub Actions и пока не исправляй код.
```

Агент может использовать `gh pr checks`, `gh run list`, `gh run view
--log-failed` и `gh run watch`. В журнале ожидаю assertion failure с различием
между `alice_smith` и `alice-smith`.

## Исправляем PR через Hermes

После подтверждения причины отправляю:

```text
Исправь намеренно сломанный тест текущего Pull Request.

После изменения запусти локальные тесты, проверь diff, сохрани исправление в
рабочей ветке и отправь её в удалённый репозиторий. Используй существующий Pull
Request. Дождись нового CI и сообщи итоговый статус GitHub checks.
```

Способ организации истории выбирается по правилам конкретного проекта: это
может быть отдельный исправляющий commit, amend, rebase или squash при merge.
Существенен наблюдаемый цикл `ошибка → диагностика → исправление → зелёный CI`.

## Завершаем Pull Request

После зелёных проверок Pull Request можно объединить принятой в проекте
стратегией. Затем обновляю локальную основную ветку и проверяю, что более свежая
версия изменения не осталась только в рабочей ветке:

```powershell
$baseBranch = gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'
git switch $baseBranch
git pull --ff-only
```

Рабочую ветку после успешного объединения можно удалить локально и удалённо.
Конкретная стратегия merge и форма истории не фиксируются этой практикой.

## Почему мы не заканчиваем после gh pr create

Теперь я фиксирую основную идею занятия.

Команда:

```text
gh pr create
```

говорит только о том, что объект Pull Request успешно создан на GitHub. Она ничего не доказывает о качестве кода.

Даже успешный локальный тест не подтверждает серверный CI.

И только:

```text
gh pr checks
```

даёт агенту текущее состояние проверок GitHub.

Это соответствует дисциплине встроенного GitHub Skill Hermes: удалённое состояние необходимо читать свежим запросом, а не выводить из локального состояния или прошлого сообщения.

## Какой результат должен получиться

Hermes проводит изменение через рабочую ветку и Pull Request, выполняет
локальную проверку, получает серверное состояние через `gh pr checks`,
наблюдает намеренно созданное падение CI, читает журнал GitHub Actions,
исправляет причину и подтверждает новый зелёный запуск.

После принятого в проекте способа объединения основная ветка содержит итоговое
изменение, а рабочая ветка не остаётся единственным местом с более свежей
версией. Локальный Git, удалённый Pull Request и внешний CI образуют единый
проверяемый процесс.
