## Что мы будем делать

Сейчас я продолжу работать с учебным проектом. Его корень далее обозначается
переменной `$projectRoot`:

```text
<каталог проекта>
```

Но сами задания я уже не буду запускать обычными сообщениями в чате. Я создам отдельную очередь Hermes Kanban.

В этой очереди будет три независимых задания. Я специально назначу им разные приоритеты и ограничу систему одним одновременно работающим агентом. Благодаря этому мы сможем увидеть настоящую очередь: одна задача выполняется, остальные остаются в состоянии `ready`.

Затем я изменю приоритет одной карточки, проверю, что она поднялась в очереди, запущу dispatcher и буду наблюдать переходы между состояниями непосредственно через веб-интерфейс Hermes.

## Проверяем профиль, который будет выполнять задачи

Сначала открываю обычный PowerShell Windows.

Открываю PowerShell в корне выбранного проекта и сохраняю вычисленный путь:

```powershell
$projectRoot = (Get-Location).Path
```

Проверяю существующие Hermes-профили:

```powershell
hermes profile list
```

Активный профиль отмечен символом `*`.

Для этой работы я создам отдельного рабочего агента, чтобы очередь не зависела от текущего интерактивного чата.

Выполняю:

```powershell
hermes profile create process-worker --clone --description "Выполняет короткие read-only задачи анализа программного проекта и возвращает проверяемый результат."
```

Параметр `--clone` копирует конфигурацию, credentials, skills и основные настройки из активного профиля, поэтому нам не требуется заново настраивать модель и провайдера. Hermes поддерживает отдельные именованные профили именно для таких независимых работников Kanban.

Проверяю профиль:

```powershell
hermes profile show process-worker
```

В результате я хочу увидеть настроенную модель и существующую конфигурацию.

Если профиль `process-worker` уже существует после предыдущего запуска практики, второй раз создавать его не нужно.

## Создаём отдельную очередь для занятия

Чтобы наши учебные задания не смешивались с другими Kanban-задачами, создаю отдельную доску.

Выполняю:

```powershell
hermes kanban boards create process-lab --name "Process Lab" --description "Учебная очередь для практики управления агентными процессами" --switch
```

Если Hermes сообщает, что такая доска уже существует, просто переключаюсь на неё:

```powershell
hermes kanban boards switch process-lab
```

Проверяю:

```powershell
hermes kanban boards show
```

Активной должна быть:

```text
process-lab
```

Hermes позволяет иметь отдельные Kanban boards для разных проектов или областей работы. У каждой такой доски своя очередь и собственная база задач.

## Ограничиваем параллельность

Теперь я специально запрещу Hermes выполнять несколько карточек одновременно.

Выполняю:

```powershell
hermes config set kanban.max_in_progress 1
```

Проверяю значение:

```powershell
hermes config get kanban.max_in_progress
```

Должно быть:

```text
1
```

Это означает, что dispatcher разрешит одновременно только одну задачу со статусом `running`. Остальные будут ждать освобождения ресурса в `ready`.

Hermes поддерживает `kanban.max_in_progress` именно как ограничение общего количества одновременно работающих Kanban workers. Если лимит уже достигнут, новые задачи остаются в очереди.

## Пока не запускаем dispatcher

Это важно.

Сейчас я сначала заполню очередь и только потом разрешу агентам её разбирать.

Если gateway уже запущен в другом PowerShell и активно выполняет Kanban-задачи, на время демонстрации можно остановить его:

```powershell
hermes gateway stop
```

Если он не был запущен, ничего делать не нужно.

Проверить состояние можно командой:

```powershell
hermes gateway status
```

Нам сейчас нужно спокойно создать три карточки и увидеть их порядок до начала исполнения.

Теперь у меня в `Ready` находятся три карточки.

Я ещё не запустил dispatcher, поэтому ни одна из них не должна находиться в `Running`.

Обращаю внимание на порядок.


должна находиться выше карточки с приоритетом `5`, а карточка с приоритетом `1` — ниже.

В Hermes очередь `ready` сортируется прежде всего по убыванию priority. При одинаковом приоритете раньше выбирается более старая задача. Этот же порядок используется dispatcher при выборе следующей работы.

## Наблюдаем первый запуск

После обновления состояния одна карточка должна перейти из:

```text

```

```text

```

или `Running`, в зависимости от отображаемого интерфейсом названия колонки.

Поскольку `kanban.max_in_progress` равен `1`, одновременно должна работать только одна карточка.

И поскольку мы изменили Priority первой карточки на `20`, именно:


должна запускаться первой.

Карточки с приоритетами `10` и `5` остаются в очереди.

Таким образом, я одновременно проверил два механизма: приоритет определяет порядок, а квота ограничивает параллельность.




Hermes хранит отдельный run для каждой попытки выполнения задачи, поэтому повторный запуск не уничтожает информацию о предыдущей попытке.

## Что мы фактически проверили

В этой практике я использовал Hermes уже как систему управления работами, а не как один чат с моделью.

Kanban board стала нашей очередью задач. `Ready` означал, что задание готово к исполнению. `Running` показывал реальную работу worker. `Blocked` позволил временно остановить карточку без её удаления. `Done` зафиксировал результат.

Приоритет управлял порядком выполнения. В очереди Hermes карточки с большим числом Priority выбираются раньше карточек с меньшим приоритетом. При одинаковом приоритете порядок определяется временем создания.

Параметр:

```text
kanban.max_in_progress = 1
```

стал нашей квотой. Независимо от количества готовых задач Hermes не запускал больше одной одновременно.

Для мониторинга мы использовали одновременно визуальную Kanban-доску и команды:

```powershell
hermes kanban watch
hermes kanban list
hermes kanban stats
hermes kanban show <ID>
hermes kanban runs <ID>
hermes kanban log <ID>
```

Таким образом, состояние работы определялось не сообщением модели «я закончил», а инфраструктурой Hermes. Именно это и превращает набор отдельных агентов в управляемый процесс.
