## 1. Что мы сегодня получим

Сейчас я продолжу работу с модулем `testing_lab` в уже открытом учебном проекте.

После предыдущей практики у меня уже есть production-код, контракт и тесты. Теперь я хочу на основании этих файлов создать документацию.

В результате в модуле должны появиться два новых файла:

```text
testing_lab\README.md
testing_lab\API.md
```

`README.md` будет точкой входа для разработчика, который впервые открыл модуль.

`API.md` будет описывать программный интерфейс модуля: функции, классы, методы, параметры, возвращаемые значения, ошибки и основные ограничения.

Здесь слово API не означает обязательно HTTP или REST API. У нашего Python-модуля тоже есть API — это публичные функции и классы, которыми пользуется другой код.

```text
Не утверждай успешность никаких проверок, которые фактически не выполнялись.
```

Этот промпт завершает нашу генерацию.

## 23. Фиксируем документацию

Если всё проверено, выполняю:

```powershell
git add testing_lab\README.md testing_lab\API.md
```

Проверяю staged diff:

```powershell
git diff --staged
```

После этого создаю commit:

```powershell
git commit -m "Практика 3.7: добавить документацию модуля возвратов"
```

Теперь документация хранится рядом с кодом и версионируется вместе с проектом.

## 24. Что именно мы автоматизировали

В этой работе Hermes не получил задачу просто «написать красивый README».

Сначала агент провёл исследование репозитория с помощью доступных в текущей сессии файловых и терминальных инструментов.

После анализа Hermes сформировал два разных документа.

`README.md` отвечает за знакомство с модулем и начало работы.

`API.md` отвечает за точное описание программного интерфейса.

После генерации тот же агент перешёл в другую роль и проверил документацию относительно исходников.

Затем мы отдельно заставили его выполнить команды, которые он указал в README.

И только после этого документацию можно считать не просто сгенерированным текстом, а проверенным артефактом проекта.

## 25. Итог практики

В результате у нас появляется такая часть проекта:

```text
testing_lab/
    __init__.py
    refunds.py
    CONTRACT.md
    README.md
    API.md
```

При этом источники информации остаются разделёнными.

`refunds.py` показывает фактический программный интерфейс.

`CONTRACT.md` определяет требуемое бизнес-поведение.

Тесты показывают, какие сценарии действительно проверяются.

`README.md` помогает новому разработчику начать работу.

`API.md` позволяет использовать публичные функции и классы без необходимости каждый раз разбирать внутреннюю реализацию.

Главный результат этой практики заключается не просто в двух Markdown-файлах. Мы построили воспроизводимую схему генерации документации: сначала исследовать реальные источники, затем создать документацию с ограничением на домыслы, после этого перепроверить её по исходникам и фактически выполнить команды, которые предлагаются пользователю.
