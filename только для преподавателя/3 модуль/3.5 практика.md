## 1. Что мы сегодня реализуем

Сейчас я соберу работающую систему автоматического review.

У меня уже есть учебный проект и удалённый GitHub-репозиторий, который мы подключали на предыдущих занятиях.

Я сначала добавлю в проект собственный стандарт code review. Затем создам отдельный Pull Request с несколькими намеренными проблемами. После этого проверю ревью вручную через Hermes, но без публикации комментариев.

Когда я удостоверюсь, что агент правильно понимает критерии, я превращу тот же процесс в автоматическую Cron-задачу Hermes.

Автоматизация будет самостоятельно искать открытые PR, получать diff, проверять его по нашим стандартам, оставлять общий комментарий, создавать точечные комментарии к строкам и, когда исправление однозначно, добавлять GitHub Suggestion.

Для анализа будет использован уже настроенный в Hermes маршрут выполнения. Отдельные учётные данные AI-сервиса в репозиторий добавлять не требуется.

Этот документ содержит обязательные правила автоматического и ручного code review учебного проекта.

## SEC-01 — Параметризованные SQL-запросы

SQL-запросы не должны строиться путём непосредственной подстановки пользовательских данных через f-string, конкатенацию строк или format.

Для PostgreSQL значения необходимо передавать отдельно через параметры драйвера.

Нарушение считается проблемой безопасности.

## ERR-01 — Ошибки не должны исчезать бесследно

Нельзя перехватывать Exception и скрывать ошибку без логирования, повторного возбуждения исключения или другой явно определённой обработки.

Код вида:

except Exception:
    return False

считается нарушением, если причина ошибки полностью теряется.

## COR-01 — Наблюдаемое поведение должно сохраняться

Изменение не должно случайно нарушать существующий публичный контракт функции, сервиса или API.

Если review обнаруживает изменение поведения, необходимо указать конкретный сценарий, в котором оно проявляется.

## ARC-01 — Ответственности должны быть разделены

Слой работы с данными должен отвечать за работу с хранилищем.

HTTP, UI и инфраструктурная логика не должны без необходимости смешиваться с repository-кодом.

## REV-01 — Только проверяемые и полезные замечания

Review не должно создавать замечание только ради замечания.

Каждый комментарий должен содержать конкретную проблему, объяснение последствий и, когда возможно, вариант исправления.

Мелкие стилистические вопросы, которые автоматически решаются formatter или linter, не следует публиковать как отдельное AI-замечание.

## SUG-01 — Suggestions должны быть безопасными и локальными

GitHub Suggestion разрешено создавать только тогда, когда исправление однозначно и не требует дополнительных бизнес-решений.

Если существует несколько архитектурно допустимых решений, необходимо описать проблему без автоматического предложения замены.

## 13. Проверяем, способен ли агент предложить правку

Для первого SQL-запроса разумная локальная правка может выглядеть примерно так:

```python
cursor.execute(
    "SELECT id, email, role FROM users WHERE email = %s",
    (email,),
)
```

Поскольку проект использует PostgreSQL, значение отделено от текста SQL.

Это хороший кандидат на GitHub Suggestion: изменение локальное и напрямую следует из `SEC-01`.

А вот вопрос о том, как именно система должна обрабатывать исключение при удалении пользователя, уже менее однозначен.

Можно логировать исключение, можно выполнять rollback, можно пробрасывать специальную ошибку.

Поэтому для `ERR-01` я скорее хочу получить комментарий с объяснением проблемы, а не автоматически предлагаемое архитектурное решение.

## 15. Почему мы добавили marker

Вот этот фрагмент:

```text
<!-- hermes-auto-review:HEAD_SHA -->
````

будет невидимым HTML-комментарием внутри GitHub.

Например:

```text
<!-- hermes-auto-review:abc123def456 -->
```

Пользователь практически не замечает его в отрисованном Markdown.

Но автоматизация сможет проверить, что именно этот commit уже был рассмотрен.

Если cron запускается повторно, а PR не изменился, повторное review не нужно.

Если разработчик отправил новый commit, `headRefOid` изменяется. Marker становится другим, и агент понимает, что необходимо проверить новую версию.

## 16. Проверяем GitHub API для inline comments

GitHub имеет отдельный REST endpoint для комментария непосредственно к строке diff. Он принимает номер PR, `commit_id`, `path`, `line` и сторону diff. Для добавленной строки используется `RIGHT`. Для многострочного комментария можно дополнительно передавать `start_line` и `start_side`.

Например, технически Hermes сможет выполнить запрос примерно такого типа:

```powershell
gh api `
  --method POST `
  "repos/OWNER/REPO/pulls/NUMBER/comments" `
  -f body="Текст замечания" `
  -f commit_id="HEAD_SHA" `
  -f path="review_demo/user_repository.py" `
  -F line=3 `
  -f side="RIGHT"
```

Я сам сейчас этот пример не запускаю.

Конкретный путь и строку должен определить reviewer из фактического diff.

GitHub CLI `gh api` автоматически формирует POST-запрос, когда передаются поля, а `-F` умеет преобразовывать числовые значения в корректные JSON-типы.

## 18. Настраиваем Tools для Cron

Теперь необходимо убедиться, что Cron-agent сможет пользоваться терминалом.

В PowerShell выполняю:

```powershell
hermes tools
```

Открывается интерфейс выбора инструментов. Переключаюсь на платформу:

```text
cron
```

Для Cron оставляю доступным как минимум терминальный toolset и чтение файлов.

Нам необходим терминал для:

```text
gh

```

и чтение файлов для:

```text

```

Не включаю ненужные browser automation или другие внешние интеграции.

Cron в Hermes поддерживает отдельную конфигурацию Toolsets, поэтому scheduled agent не обязан автоматически получать все возможности обычного интерактивного агента.

Если в установленной версии интерфейс не показывает отдельную платформу `cron`, проверяю доступность терминала и чтения файлов в разделе Cron Dashboard или в документации установленной версии Hermes. Названия разделов интерфейса могут различаться, но Cron-сессии должны иметь доступ к этим двум группам инструментов.

## 19. Создаём Cron-задачу сначала в paused-режиме

Я не хочу, чтобы новая автоматизация сразу начала комментировать GitHub по расписанию.

Поэтому сначала создаю её остановленной.

Читаю prompt в переменную PowerShell:

```powershell
$reviewPrompt = Get-Content ".\automation\pr-review-prompt.txt" -Raw
```

Теперь создаю задачу:

```powershell
hermes cron create `
  "every 30m" `
  $reviewPrompt `
  --name "pr-review-demo" `
  --skill github-code-review `
  --workdir $projectRoot `
  --deliver local `
  --paused `
  --paused-reason "Учебная проверка перед автоматическим запуском"
```

Параметр `--workdir` здесь особенно важен. Без него Cron-сессия запускается вне репозитория, поэтому проектные файлы и текущий Git-контекст могут быть недоступны. В актуальном Hermes `--workdir` привязывает scheduled run к конкретному каталогу и делает его рабочей областью инструментов.

## 20. Проверяем созданную автоматизацию

Выполняю:

```powershell

```

Ищу:

```text
pr-review-demo
```

Задача должна отображаться как paused.

Дополнительно:

```powershell
hermes cron status
```

Теперь я знаю, что задача существует, но сама по расписанию пока не запускается.

Hermes позволяет создавать Cron job сразу с `--paused`, поэтому между созданием и первым автоматическим запуском нет опасного промежутка.

## 23. Запускаем автоматическое review вручную

Хотя Cron job находится в paused-состоянии, оператор всё равно может выполнить ручной запуск.

Выполняю:

```powershell

```

Ручной запуск в Hermes разрешён даже для paused job: пауза останавливает автоматические срабатывания, но не запрещает оператору выполнить canary-run.

Теперь агент запускается уже не в нашем обычном чате.

Это отдельная автоматическая Cron-сессия.

## 26. Проверяем inline comments

Теперь на странице PR нажимаю:

```text
Files changed
```

Около проблемной строки должен появиться комментарий Hermes.

Например, для SQL-запроса я ожидаю замечание примерно такого смысла:

```text
SEC-01: пользовательское значение email напрямую включается в SQL через f-string.

Это позволяет содержимому email изменить структуру SQL-запроса.

Используйте параметризованный запрос.

Project Code Review Standards: ...
```

Мне важно увидеть, что комментарий находится рядом с конкретной строкой diff.

Это уже не общий chat-response, а настоящее PR-review.

## 27. Проверяем GitHub Suggestion

Если Hermes признал исправление однозначным, под inline comment должен появиться блок GitHub Suggestion.

Например:

```python
cursor.execute(
    "SELECT id, email, role FROM users WHERE email = %s",
    (email,),
)
```

GitHub визуально отображает такой блок как предлагаемое изменение.

Я не нажимаю автоматическое применение сразу.

Сначала проверяю, действительно ли предложение соответствует `SEC-01`.

Это важно: AI Suggestion остаётся предложением, а не автоматическим изменением production-кода.

## 28. Как GitHub Suggestion устроен технически

В тексте review comment специальный Markdown выглядит так:

````text
```suggestion
новый код
```
````

Если комментарий привязан к нужной строке или диапазону строк diff, GitHub показывает возможность применить предложенную замену.

Для многострочного предложения API использует:

```text
start_line
start_side
line
side
```

GitHub рекомендует использовать именно line-based параметры; старый параметр `position` постепенно выводится из основного сценария.

## 29. Проверяем, что автоматизация не дублирует review

Теперь ничего в PR не изменяю.

Снова выполняю:

```powershell
hermes cron run pr-review-demo
```

Затем:

```powershell
hermes cron tick
```

Автоматизация снова увидит открытый PR.

Но HEAD SHA тот же.

В существующем комментарии уже находится:

```text
<!-- hermes-auto-review:HEAD_SHA -->
```

Поэтому агент должен определить, что эта версия уже проверена, и не создавать второй идентичный набор комментариев.

Проверяю количество обычных комментариев:

```powershell
gh pr view $pr --json comments --jq ".comments | length"
```

Оно не должно увеличиваться из-за повторного review той же версии.

## 30. Обновляем Pull Request

Теперь продемонстрирую, что после нового commit review должно выполняться снова.

Я могу воспользоваться GitHub Suggestion.

На вкладке:

```text
Files changed
```

нахожу предложенное изменение.

Если GitHub показывает кнопку:

```text
Commit suggestion
```

нажимаю её.

GitHub предлагает создать commit.

Нажимаю подтверждение изменения.

Теперь head-commit Pull Request изменился.

Проверяю из PowerShell:

```powershell
gh pr view $pr --json headRefOid --jq ".headRefOid"
```

SHA уже другой.

Следовательно, старый marker больше не соответствует текущей версии.

## 31. Запускаем review новой версии

Снова выполняю:

```powershell
hermes cron run pr-review-demo
```

```powershell
hermes cron tick
```

Теперь агент не должен пропустить PR.

Он увидит новый:

```text
headRefOid
```

и выполнит review заново.

Если первый SQL-запрос уже исправлен, соответствующее замечание исчезнет.

Но другие проблемы, например второй SQL-запрос или:

```python
except Exception:
    return False
```

могут остаться.

Так мы проверяем, что automation работает с версиями Pull Request, а не просто однажды запоминает его номер.

## 32. Проверяем review из командной строки

Обычные комментарии можно посмотреть:

```powershell
gh pr view $pr --comments
```

Inline review comments можно запросить через GitHub API.

Сначала:

```powershell
$repo = gh repo view --json nameWithOwner --jq ".nameWithOwner"
```

Затем:

```powershell
gh api "repos/$repo/pulls/$pr/comments"
```

Если хочу увидеть только полезные поля:

```powershell
gh api "repos/$repo/pulls/$pr/comments" `
  --jq '.[] | {path, line, body, html_url}'
```

Так я могу проверить, какие именно inline comments создала автоматизация.

## 33. Проверяем, что Hermes ничего не изменял сам

Теперь я отдельно проверяю локальный проект:

```powershell
git status
```

Cron-reviewer не должен самостоятельно исправлять локальные файлы.

Он только анализирует diff и публикует review.

Также проверяю Pull Request.

Ни один комментарий не должен автоматически изменить состояние Pull Request.

Это соответствует нашей модели безопасности: reviewer анализирует и предлагает, а изменение принимает разработчик.

## 34. Что делать с ложноположительным замечанием

Представим, что Hermes оставил комментарий, который я считаю неправильным.

Я не меняю код только потому, что комментарий создал AI.

Сначала открываю указанное правило в:

```text
docs/review-standards.md
```

Затем проверяю фактическое поведение кода.

Если правило не нарушено, комментарий считается false positive.

Это важная часть практики: качество автоматического review мы оцениваем по подтверждённым дефектам, а не по количеству созданных AI-комментариев.

Если определённый тип ложных замечаний повторяется, я меняю стандарт или автоматический prompt, а не прошу разработчиков каждый раз игнорировать одинаковый шум.

## 35. Включаем настоящее автоматическое расписание

До этого job был paused и запускался только вручную.

После проверки я могу включить автоматический polling:

```powershell
hermes cron resume pr-review-demo
```

Проверяю:

```powershell
hermes cron list
```

Теперь:

```text
pr-review-demo
```

запускается:

```text
every 30m
```

Hermes на каждом срабатывании создаёт новую агентную сессию, загружает указанный Skill и выполняет prompt. Skill-backed cron jobs поддерживаются штатно, причём `--workdir` позволяет привязать такую сессию к конкретному репозиторию.

## 36. Для занятия снова ставим автоматизацию на паузу

После демонстрации я не хочу бессмысленно запускать модель каждые 30 минут.

Поэтому выполняю:

```powershell
hermes cron pause pr-review-demo
```

Проверяю:

```powershell
hermes cron list
```

Автоматизация сохранена, но больше не запускается по расписанию.

Когда она понадобится снова:

```powershell
hermes cron resume pr-review-demo
```

Таким образом, вся система остаётся настроенной.

## 37. Завершаем учебный эксперимент

После проверки закрываю тестовый Pull Request без слияния, потому что намеренно небезопасный пример не должен попадать в основную ветку:

```powershell
gh pr close $pr --comment "Учебная проверка завершена; тестовая ветка удаляется без слияния."
```

Возвращаюсь на основную ветку и удаляю тестовую ветку локально и на удалённом репозитории:

```powershell
git switch $defaultBranch
git branch -D review/unsafe-user-repository
git push origin --delete review/unsafe-user-repository
git fetch --prune
```

Проверяю итоговое состояние:

```powershell
git branch --all
git status
```

В актуальном состоянии остаётся основная ветка с документами практики, а закрытый Pull Request сохраняет историю выполненного review.

## 38. Что в этой схеме является автоматическим

Теперь я разбираю итоговую архитектуру.

GitHub хранит Pull Request и его diff.

GitHub CLI выступает техническим интерфейсом между Hermes и GitHub.

Hermes Cron периодически запускает reviewer.

`github-code-review` Skill задаёт специализированный процесс работы с PR. Он поставляется вместе с Hermes и предназначен для анализа GitHub Pull Request.

`docs/review-standards.md` задаёт правила именно нашего проекта.

Модель анализирует изменение.

Обычный `gh pr comment` создаёт итоговое резюме.

GitHub REST API создаёт точечные комментарии непосредственно на строках diff.

GitHub Suggestion позволяет предложить небольшой конкретный patch, но не применяет его без решения разработчика.

## 39. Чем этот вариант отличается от запуска анализа в GitHub Actions

Обратите внимание: GitHub Actions здесь не запускает анализ.

Reviewer работает в Hermes на нашей машине или на той инфраструктуре, где запущен Hermes Gateway.

Hermes использует настроенный для текущего окружения маршрут выполнения. Конкретный способ подключения не является частью логики reviewer и может меняться без изменения репозитория.

Для доступа к GitHub используется существующая авторизация:

```text
gh auth login
```

Эта авторизация относится только к операциям с GitHub.

## 40. Ограничение нашей реализации

У polling есть один очевидный компромисс.

Review начинается не непосредственно в момент события GitHub, а когда срабатывает очередная проверка Cron.

Для учебного проекта это удобно: нам не нужен публично доступный сервер, домен и webhook endpoint.

Если в дальнейшем нужна мгновенная реакция на `pull_request.opened` или `pull_request.synchronize`, Hermes поддерживает отдельную webhook-схему. Но официальная документация прямо рекомендует polling-вариант как более простой путь, если публичного endpoint нет.

## 41. Итог практики

В результате я получил полноценный автоматизированный reviewer, не привязанный в коде проекта к конкретной модели или способу её подключения.

У меня есть проектный стандарт review.

Есть проверяемая история тестового Pull Request.

Hermes получает его diff непосредственно с GitHub.

Агент проверяет корректность, безопасность, обработку ошибок и архитектурные правила.

Замечания привязываются к конкретным правилам проекта.

Для локального и однозначного исправления агент может создать GitHub Suggestion.

Для каждого проверенного HEAD commit сохраняется marker, поэтому одна и та же версия PR не комментируется бесконечно.

После нового commit review запускается снова.

Главное здесь заключается в том, что мы автоматизировали не просто генерацию текста с фразой «код выглядит плохо». Мы создали воспроизводимый процесс: получить конкретный diff, проверить его по формализованным критериям, оставить проверяемые замечания непосредственно в Pull Request и дать разработчику возможность принять или отклонить предложенную правку.
